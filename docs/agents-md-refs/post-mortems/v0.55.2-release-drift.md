# Post-mortem: v0.55.2 release drift — SW-028..SW-031 working-tree reversion

**Date:** 2026-07-30
**Author:** agent-4244dfee (investigation owner per SW-033)
**Severity:** Low (release on origin/main was intact; only local working tree diverged)
**Status:** Resolved by SW-032 (`bdc92a7`); this report is the post-incident analysis.

## TL;DR

The drift the engineer reported in `msg-ce305ab5` was not caused by `npm install`,
an un-bumped build, or a stale worktree. It was a **deliberate operator-mandated
rollback** (SW-028, `27188f7`) that restored the working tree to v0.55.1
immediately after the v0.55.2 release shipped. The `dist/skills.d.ts#STELOW_PLUGIN_VERSION
= "0.54.3"` the engineer observed was a stale gitignored build artifact left over
from the SW-008 v0.55.0 historical miss — never re-baked across SW-027 through
SW-031 because none of those tasks ran `npm run prepare:fusion-plugin && npm run
build:fusion-plugin` against the post-release source.

**Bisect point:** `27188f7` (SW-028) — the only commit in `e3e1ed5..bdc92a7`
that touches any of the seven tracked version-bearing files.

**Lockfile drift:** none. Across the full range the five JSON surfaces stay in
lockstep (package.json, package-lock.json root, package-lock.json
`packages[""].version`, manifest.json, plugin package.json) and the TypeScript
`STELOW_PLUGIN_VERSION` follows them. There is no fifth misaligned file the
6-point check misses.

**Proposed guard:** A `dist/skills.d.ts` drift detector in CI (the open SW-009-
style guard already noted in agent memory), plus a commit-message convention
that flags any `package.json#version` change on a commit whose HEAD tag is a
different release — those together catch the next instance of the actual root
cause (committed source rollback without a matching dist re-bake) and the
adjacent failure modes (a/b/c).

## Hypothesis evaluation

### (a) Stale worktree / branch state — RULED OUT

The hypothesis: each SW-029/030/031 executor branched from a pre-SW-027 commit,
so its working tree started at v0.55.1 and the merges reintroduced the older
state.

Evidence against:

```bash
$ git merge-base fusion/sw-029 e3e1ed5   # e3e1ed54b910b81cf04d94c37ec6b900df0699cd
$ git merge-base fusion/sw-030 e3e1ed5   # e3e1ed54b910b81cf04d94c37ec6b900df0699cd
$ git merge-base fusion/sw-031 e3e1ed5   # e3e1ed54b910b81cf04d94c37ec6b900df0699cd
```

All three merge bases are `e3e1ed5` itself — the SW-027 release commit. The
branches were correctly forked from the post-release tip.

For SW-028, no local branch survives (it was fast-forwarded into main and
cleaned up), but the SW-028 executor log shows it ran on `fusion/sw-028` with
HEAD at `e3e1ed5`. The agent's own preflight check recorded `git log --oneline
origin/main..HEAD` was empty (no local commits ahead of origin) and the staged
patch was the seven-file restore.

So every branch in the range was correctly based on the v0.55.2 release tip.
**Stale-worktree hypothesis ruled out.**

### (b) `npm install` side effect on `package.json` / `package-lock.json` — RULED OUT

The hypothesis: an `npm install` invocation rewrote `package.json` or
`package-lock.json` due to a lockfile/registry mismatch, downgrading the
version field.

Evidence against:

1. The version field transitions happen **exactly once**, at `27188f7`. The
   commit's `git show` shows `package.json` and `package-lock.json` lines
   hand-edited (`-`/`+` lines are explicit string substitutions), not a
   wholesale regeneration. Compare with a real `npm install` rewrite, which
   would show tens of thousands of lines of indentation/whitespace churn.
2. `git log --follow package-lock.json e3e1ed5..bdc92a7 --oneline` returns
   only the three commits that legitimately touched it: `e3e1ed5` (SW-027
   bump), `27188f7` (SW-028 rollback), `bdc92a7` (SW-032 re-bake). SW-029
   ran `npm install` in the merge clean room (per the merger log: *"Syncing
   dependencies for AI merge clean room: npm install"*) but the resulting
   worktree was ephemeral — its lockfile churn never propagated to the
   committed state.
3. The `package-lock.json` diff in `27188f7` is the minimal text edit
   (`±4` lines: root `"version"`, `packages[""]."version"`), not the
   multi-section churn typical of `npm install`.

**`npm install` side-effect hypothesis ruled out.**

### (c) `npm run build:fusion-plugin` against un-bumped source — PARTIALLY SUPPORTED (for `dist/skills.d.ts` only)

The hypothesis: the build pipeline regenerated `dist/skills.d.ts` from a source
that hadn't been re-bumped, so the built artifact desynced from the source.

Evidence — partial support, scoped:

The SW-029 merger (in the clean room) ran `npm run build` at 13:51:34Z, which
executes `prepare:fusion-plugin && build:fusion-plugin`. At that moment
`src/skills.ts#STELOW_PLUGIN_VERSION = "0.55.1"` (post-SW-028), so the rebuilt
`dist/skills.d.ts` would have been 0.55.1 — **but only inside the clean room**.
`dist/` is gitignored, so the rebuild never reached the committed state.

The `0.54.3` value the engineer observed on the main worktree's
`dist/skills.d.ts` is **not from SW-029's clean-room rebuild**. It is the
leftover from the SW-008 historical miss (SW-008 shipped v0.55.0 with
`STELOW_PLUGIN_VERSION` baked at 0.54.3 because the release commit skipped
step 3; SW-010 v0.55.1 fixed this as a side-effect on the main worktree, but
the build artifacts in any given worktree are whatever was last generated
locally).

So hypothesis (c) is correct in shape (the build does regenerate `dist/` from
source), but **not** the cause of the 0.54.3 observation. The cause is that
**none of SW-027, SW-028, SW-029, SW-030, or SW-031 ran
`prepare:fusion-plugin && build:fusion-plugin` on the main worktree after the
v0.55.2 release**. SW-027's step 3 was the only re-bake, and only in the
SW-027 clean room; the main worktree's local `dist/skills.d.ts` predates the
SW-027 re-bake and was never refreshed there. SW-032 closed this by re-running
step 3 on the main worktree.

**Build-against-un-bumped-source hypothesis: supported for `dist/skills.d.ts`
stale-state, not supported for the source version reversion.**

## Actual root cause

**Deliberate, operator-mandated rollback of the v0.55.2 source-side version
bumps, committed as SW-028 (`27188f7`) immediately after the v0.55.2 release.**

Evidence:

1. The SW-028 PROMPT.md (verbatim): *"The working tree on `main` currently
   contains STAGED changes that match the SW-026 acceptance criteria exactly"*.
   This is a pre-staged seven-file restore — someone put the rollback on the
   index before SW-028 was created, and SW-028's job was to commit it.
2. The SW-028 PROMPT.md commits to: *"Single commit, message:
   `chore(SW-026): restore working tree to canonical v0.55.1`"* and
   *"Roll back the version field on all six packaging surfaces from v0.55.2
   to v0.55.1"* — explicit, intentional, well-documented rollback. The executor
   substituted `SW-028` for `SW-026` in the commit subject (per Fusion's task-ID
   convention) but the substantive change is identical.
3. The commit body names the intent: *"returning the default branch to the
   published v0.55.1 release state."* It is not framed as a fix, not framed as
   a regression — it is a deliberate canonical-baseline restore.
4. The merge is squashed onto `main` with no force-push or history rewrite;
   the v0.55.2 tag and gh release on `origin/main` are preserved byte-identical.
   This rules out an accidental or mistaken regression — the operator knowingly
   kept the v0.55.2 release artifacts while downgrading the working-tree source.

The two follow-on test fixes (SW-029/030/031) are unrelated; they just happened
to land on top of the rollback.

**This is not a SW-008-style stale-version side effect.** It is a different
release arc — one where the release shipped correctly but the working tree was
subsequently rolled back. The published release is intact; the local tree is
intentionally one minor version behind.

### Why did the operator roll back?

Two plausible rationales (operator intent is not directly recoverable from the
git log; this report names them as candidate interpretations, not confirmed
facts):

1. **Retraction.** The operator decided v0.55.2 was released in error and
   needed to be retracted at the source level — keeping the gh release for
   already-notified downstream consumers but bringing the working tree back
   to a known-good state. The eventual `bdc92a7` re-bake contradicts this:
   if the intent were retraction, SW-032 would not have re-baked v0.55.2.
2. **Deferral to v0.55.3.** The operator wanted to fold the SW-025/SW-026
   content into a v0.55.3 release instead of v0.55.2 (which was meant as a
   pure release-recipe validation). The `bdc92a7` re-bake aligns with this:
   the source tree returns to v0.55.2 because v0.55.3 will be cut from the
   current state, and a v0.55.3 cut needs the v0.55.2 source to bump onto.

The deferral interpretation is consistent with the `CHANGELOG.md` change in
SW-028 (the v0.55.2 release section was demoted to `## [Unreleased]`) and with
the project memory note: *"v0.55.3 release work deferred to a separate
planning task"*. **But this report does not adjudicate intent** — it only
documents what the commit log says happened.

## False leads considered

These were investigated and ruled out before settling on the actual cause:

1. **"A merge conflict resolution introduced the reversion."** False. The
   SW-028 merge was a single-commit fast-forward (no merge conflict). The
   SW-029 squash comment notes: *"No conflicts to resolve — both files were
   only modified on the task branch, not on the integration tip."* (which
   was `27188f7`).
2. **"A post-merge hook auto-rolled-back version fields."** False. No such
   hook exists in the repository; no `.git/hooks/` symlinks or
   `.husky/post-merge` config is present.
3. **"`npm ci` (vs `npm install`) would have prevented this."** Would have
   helped if the rollback had been a lockfile/registry artifact, but per §(b)
   the rollback is hand-edited source — `npm ci` does not edit
   `package.json#version` itself.
4. **"SW-029 ran `npm run build` in the main worktree and re-baked 0.55.1
   into `dist/skills.d.ts`."** Partially true but unrelated to the source
   reversion. SW-029's build run was in the clean room; the main worktree's
   `dist/skills.d.ts` was never touched by SW-029.
5. **"The engineer's `dist/skills.d.ts = 0.54.3` observation is from SW-028's
   own build run."** False. SW-028's commit body names `src/skills.ts` and
   `package.json` but does not name `dist/skills.d.ts`, and `dist/` is
   gitignored so any re-bake inside SW-028's clean room would not propagate.
   The 0.54.3 is older than SW-027's re-bake — it predates the SW-027 release.

## Proposed guard

The actual root cause is **deliberate source-side rollback that omits a
matching `dist/` re-bake**. None of the three PROMPT-proposed guards (a/b/c)
match this — they all target accidental side-effects, not intentional
multi-file commits. The right guard is one that catches the next instance of
the actual root cause:

### Primary guard — commit-message contract + tag-aware pre-push check

Two-part, lightweight, and runs in CI without slowing the merge pipeline:

1. **Commit-message contract for any commit that edits `package.json#version`.**
   Require the commit body to contain one of:
   - `Release-Bump: v<X.Y.Z>` trailer — for legitimate release bumps (matches
     the existing AGENTS.md "Versioning" step 1), OR
   - `Rollback: v<X.Y.Z> → v<A.B.C> — <reason>` trailer — for deliberate
     rollbacks, where the reason must be present.

   The trailer forces a clear operator intent declaration and gives the
   follow-up release engineer a search handle (`git log --grep='^Rollback:'`
   returns every intentional rollback).

2. **Tag-aware CI step (`scripts/check-version-coherence.sh`)** that runs on
   every PR touching `package.json`, `package-lock.json`,
   `plugins/fusion-plugin-stelow/manifest.json`, `plugins/fusion-plugin-stelow/package.json`,
   or `plugins/fusion-plugin-stelow/src/skills.ts`:

   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   head_version="$(node -p "require('./package.json').version")"
   latest_tag="$(git describe --tags --abbrev=0 origin/main 2>/dev/null || echo none)"
   if [[ "$latest_tag" != "none" ]]; then
     tag_version="${latest_tag#v}"
     if [[ "$head_version" != "$tag_version" ]] && \
        ! git log --format='%B' -1 HEAD | grep -qE '^(Rollback|Release-Bump):'; then
       echo "::error::package.json#$head_version differs from latest tag v$tag_version without a Rollback/Release-Bump trailer"
       exit 1
     fi
   fi
   ```

   This catches the actual root cause (committed rollback without a declared
   intent) and the most common adjacent failure (forgotten `npm version` in a
   release commit).

### Secondary guard — `dist/skills.d.ts` drift detector (existing open improvement)

The `dist/skills.d.ts = 0.54.3` observation came from a stale gitignored
artifact that no commit ever refreshed. This is the open SW-009-style guard
already noted in agent memory. Concretely:

- **In CI** (`verify` job, after `npm run build:fusion-plugin`):
  ```bash
  test "$(grep -oE '"[0-9]+\.[0-9]+\.[0-9]+"' plugins/fusion-plugin-stelow/dist/skills.d.ts | head -1 | tr -d '"')" \
    = "$(node -p "require('./plugins/fusion-plugin-stelow/manifest.json').version")"
  ```
  This is the canonical SW-008 historical-miss detector. Implementing it
  would have caught the engineer's 0.54.3 observation at PR-merge time
  (assuming `dist/` were rebuilt in CI) — though note it does **not** catch
  a local-only stale `dist/skills.d.ts` if the commit itself doesn't touch
  the version surfaces.

The primary guard is sufficient to catch the next instance of the actual root
cause. The secondary guard catches an adjacent class of failures (stale
generated artifacts from any cause, including the SW-008 historical pattern).
**Both should be implemented; the primary is in scope for v0.55.3+, the
secondary is the existing open improvement.**

## Recommended next action for v0.55.3+

1. **File the primary guard as a v0.55.3 task.** The commit-message contract
   plus tag-aware CI script is small (`scripts/check-version-coherence.sh` is
   ~15 lines, plus a hook into the existing CI workflow). Target: SW task under
   the next release mission.
2. **Adopt the commit-message convention going forward.** Even before the CI
   guard lands, future executors should write `Release-Bump:` or `Rollback:`
   trailers when they touch `package.json#version`. The next release engineer
   will be able to `git log --grep='^Rollback:'` to find every intentional
   rollback and reason about their safety.
3. **No code changes to v0.55.2 itself.** The v0.55.2 release is correct;
   SW-032's `bdc92a7` re-bake restored working-tree coherence. Do not amend
   or re-tag `e3e1ed5` (per SW-032's don'ts and the project memory entry
   on this arc).
4. **Re-audit any task that ever ran `npm install` in a non-clean-room
   worktree.** SW-029's merger ran it in a clean room (safe); no other task
   in the range ran it on a tracked worktree. This is a known clean-room
   pattern and does not need a new guard.
