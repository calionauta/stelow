🚀 Mission Control
para o stelow

Um sistema web que consome issues do Linear, orquestra workflows do stelow via Pi, exibe estágios, artefatos e escopos em tempo real, e permite gates com Plannotator embutido — tudo acessível para PMs, UX designers e devs sem precisar abrir um terminal.

🔧 stelow extension + web app 🔗 Linear API + Webhooks 🖥️ xterm.js + Plannotator embed 🧑‍🚀 Human-in-the-loop

🧭 Visão Geral

O conceito central: um "Mission Control" web que é o cérebro visível do stelow. Ele não substitui o terminal — ele o torna opcional para quem só precisa acompanhar, responder perguntas e aprovar gates.

🧠 O que o Mission Control faz

Consome dados de ferramentas externas (Linear, GitHub Issues) — lê issues, projetos, comentários, status. Cria e atualiza issues refletindo o progresso do workflow.

Exibe tudo ao vivo — workflows em andamento, macro-estágios (Shape → Build → Verify), artefatos por fase, escopos com dependências, tarefas com progresso.

Requer atenção humana — destaca onde o humano precisa agir: perguntas para responder, gates para aprovar, escopos para revisar.

🎯 O que NÃO faz

Não substitui o Pi ou o terminal. A orquestração do workflow (rodar skills, gerar artefatos) continua sendo feita pelo agente de IA no terminal.

Não é "mais uma ferramenta" — é uma superfície de visualização e interação que se acopla ao ecossistema existente. O PM vê o que precisa aprovar no navegador. O dev vê o progresso dos scopes no Linear.

Não substitui o Plannotator — o embute ou abre como link.

🏗️ Arquitetura Proposta

Seis camadas que se comunicam via WebSockets, webhooks e API REST. O dado central é o stelow.json — o terminal escreve, o Mission Control lê e exibe.

Externo Linear (API) ↔ GitHub Issues ↔ Slack (notify)
Web App Mission Control ← Next.js / Fastify WebSocket Server xterm.js Terminal
Browser Plannotator (embed/iframe) ⤴ .plannotator/approvals/
Terminal Pi + stelow extension → $ /sw-start, /sw-next → Skills / Stages
Estado stelow.json ← .stelow/{date}/{hash}/ artifacts (specs, plans...)
Daemon stelow daemon (Node) → WebSocket broker → File watcher (chokidar)
💡

O segredo da arquitetura: O daemon (camada 6) fica rodando no mesmo ambiente do Pi. Ele escuta stelow.json e o diretório .stelow/ com um file watcher. A cada mudança, ele transmite via WebSocket para o Mission Control. O terminal nunca precisa "saber" que existe um web app — ele só escreve arquivos como sempre fez.

🧩 Componentes do Sistema

Cada peça que precisaria ser construída ou adaptada, com o que já existe e o que é novo.

  • 1
    Daemon stelow — Processo Node que observa o sistema de arquivos, gerencia WebSocket connections, e faz sync bidirecional com ferramentas externas (Linear). NOVO
  • 2
    File Watcher — Usando chokidar, observa stelow.json e diretórios de artefatos. A cada mudança, emite evento via WebSocket. Zero polling. NOVO
  • 3
    WebSocket Server — Bridge entre o daemon (local) e o Mission Control (web). Transmite estado, recebe comandos de ação. NOVO
  • 4
    Mission Control Web App — Interface web com dashboard de workflows, scopes, artefatos, e área de perguntas/gates. Pode ser um app Next.js (SSR) ou um frontend estático com backend Fastify. NOVO
  • 5
    Linear Adapter — Módulo que sincroniza stelow ↔ Linear. Cria issues no Linear quando um workflow começa. Comenta cada avanço de fase. Atualiza status quando scopes mudam. Escuta webhooks do Linear para detectar respostas. NOVO
  • 6
    Plannotator Integration Layer — Abre Plannotator no browser (ou embute). Escuta o retorno --json para capturar decisões. Já existe no stelow como CLI + tool, mas precisa de uma interface programática para o web app. ADAPTAR
  • 7
    Terminal Stream — Usando xterm.js + node-pty ou ttyd, exibe o terminal do Pi ao vivo no navegador. Permite que PMs vejam o agente "pensando" em tempo real, sem abrir terminal. NOVO
  • 8
    Quest Core (Question Engine) — Motor que decide quando e como perguntar ao humano. Lê o review_mode do workflow, gera documentos de pergunta, envia para o canal apropriado (web UI, Linear comment, ou deixa o Pi perguntar via terminal). NOVO

🔗 Integração com Linear

A ideia é o stelow "falar a língua" do Linear — criar issues, comentar progresso, atualizar status, mas sem depender do Linear para o core do workflow.

linear.app — stelow workflow visível no board
╔══════════════════════════════════════════════════════════════╗ ║ 🔍 stelow / Produto | ● 3 Active | 12 Done ║ ╠══════════════════════════════════════════════════════════════╣ ║ ║ ║ workflow "Feature: User Onboarding" Shape | ● ║ ║ ───────────────────────────────────────────── ║ ║ workflow "Bugfix: Login 500 error" Execution scopes 4/6 ║ ║ ───────────────────────────────────────────── ║ ║ workflow "New: Payment Gateway" Gate ⏳ NEEDS REVIEW ║ ║ ───────────────────────────────────────────── ║ ║ workflow "Refactor: Auth module" Verify scopes 8/8 ║ ║ ║ ╚══════════════════════════════════════════════════════════════╝

🔄 Sync de Fluxo (stelow → Linear)

Workflow criado → Issue criada no Linear com título, descrição e label "stelow".

Fase avança → Comentário na issue: "✅ Shape concluído. Entrando em Gate."

Scope muda → Subtarefas criadas/atualizadas no Linear.

Workflow concluído → Status → Done, comentário final com audit trail.

📡 Webhooks (Linear → stelow)

Comentário novo → Se alguém responde a uma pergunta do stelow no Linear, o webhook dispara e o daemon coleta a resposta.

Issue movida → Se um PM arrasta uma issue de "In Progress" para "Done" no board, o daemon interpreta como "scope concluído".

Label adicionada → "blocked" → daemon pausa o workflow.

⚠️ Limitações do Linear

Sem custom fields — Estado do stelow (appetite, review_mode, dirHash) precisa ser armazenado na descrição da issue em formato YAML frontmatter ou em labels convencionadas.

Não é blocking — Linear não tem "gate blocking". O bloqueio precisa ser lógico (no daemon), não no Linear.

🔑

Decisão de design: O Linear é superfície de visualização e comunicação, mas não de decisão. As perguntas críticas e gates continuam no Mission Control (web) ou no Plannotator. O Linear mostra "esse workflow precisa de atenção → abra o Mission Control".

🖥️ Terminal Ao Vivo no Browser

Uma das maiores fricções hoje: PMs e designers não têm como ver o que o agente está fazendo. Com terminal streaming, eles podem assistir ao vivo sem instalar nada.

🟢 stelow — Terminal Session: "Payment Gateway"
┌─────────────────────────────────────────────────────────────┐ │ $ pi │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ ◆ stelow: Shape Up Planning — "Payment Gateway" │ │ │ │ /sw-start initializing workflow... │ │ │ │ ───────────────────────────────────────────────────────── │ │ │ │ setup:15 How deep should the plan be? │ │ │ │ ┃ ○ Lean — Quick validation, 1 scope │ │ │ │ ┃ ● Core — One feature, 3-5 scopes ← selecionado │ │ │ │ ┃ ○ Complete — Full pipeline, 8-15 scopes │ │ │ │ ───────────────────────────────────────────────────────── │ │ │ │ ⏳ Agent is shaping the proposal... │ │ │ │ Analyzing problem: 'Implementar gateway de pagamento...' │ │ │ │ Mapping rabbit holes... │ │ │ └─────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘

⚙️ Como funciona

xterm.js no frontend (mesmo usado pelo VS Code).

node-pty no backend — cria um PTY real conectado ao shell do projeto.

WebSocket bidirecional — streaming de output, envio de input.

Múltiplas sessões — uma por workflow, ou um terminal compartilhado.

🔒 Segurança

Sessões são read-only por padrão — PMs veem mas não podem digitar comandos. Apenas devs autenticados podem interagir.

Ou: o terminal é visível mas bloqueado — o PM só pode responder perguntas via UI, não via terminal.

📦 Opções de implementação

ttyd — mais simples, já pronto. Só não dá tanto controle de UI.

xterm.js + node-pty custom — mais flexível, permite embed direto no Mission Control, controle de permissões, múltiplas sessões com labels.

💡

Insight: O terminal ao vivo resolve um problema que nem sabíamos que existia. Hoje PMs não têm visibilidade do que o agente está fazendo — quando veem o terminal rolando, entendem o ritmo, veem o agente "pensando", e confiam mais no processo. É o real-time feel que falta.

❓ O Coração do Problema: Como Fazer as Perguntas

Esta é a parte mais crítica e a que você mais refletiu. Existem 3 alternativas claras, cada uma com trade-offs diferentes. Vamos a elas.

OPÇÃO A — RECOMENDADA

A — Plannotator adaptado como "Question Doc"

🎯 Transformar cada pergunta em um documento markdown → abrir no Plannotator

Em vez de ask_user_question no terminal, o workflow gera um documento de perguntas em markdown com checkboxes interativos. Esse documento é aberto no Plannotator no browser. O usuário seleciona opções, anota, aprova. O feedback volta como JSON.

Agent→ [Escreve question-doc.md com perguntas e checkboxes]
→ [Abre Plannotator com --gate --json]
┌─ Plannotator (browser) ──────────────────┐
│ Appetite: How deep should the plan be? │
│ ● Core — One feature, 3-5 scopes │
│ ○ Lean — Quick validation │
│ ○ Complete — Full pipeline │
│ [Approve] [Annotate] │
└────────────────────────────────────────────┘
User→ [Seleciona "Core", aprova]
Plann→ { "decision": "approved", "selections": { "appetite": "Core" } }
Agent→ [Continua o workflow com appetite=Core]
✅ Vantagens
  • Não requer componente novo — Plannotator já existe
  • Já tem blocking gate semantics
  • Feedback estruturado via annotations ou JSON
  • Todos os usuários acessam via browser
  • Aproveita o approval receipt existente
⚠️ Desafios
  • Plannotator foi feito para revisão, não para questionários
  • Checkboxes funcionam visualmente, mas o retorno JSON pode não incluir o estado dos checkboxes — precisa testar
  • Multi-select pode não ter UX ideal
  • Se o Plannotator não suportar, precisamos adaptar ou criar algo
OPÇÃO B

B — Web UI própria para perguntas + Plannotator para gates

🎯 Criar um componente de questionário embutido no Mission Control

O Mission Control tem uma área dedicada a perguntas. Quando o workflow precisa de uma decisão humana, o daemon emite um evento "pergunta pendente". O web app exibe a pergunta com opções, multi-select, preview, etc. O usuário responde ali mesmo. Plannotator continua sendo usado apenas para os gates visuais (revisão de spec, diff review).

Daemon→ [WebSocket: { type: "question", id: "...", payload: {...} }]
→ [Mission Control exibe pergunta com radio buttons]
┌─ Mission Control ────────────────────┐
│ 🤔 Pergunta pendente │
│ How deep should the plan be? │
│ ○ Lean ○ Core ○ Complete │
│ [Responder] │
└────────────────────────────────────────┘
User→ [Clica "Core", "Responder"]
Daemon→ [WebSocket: { type: "answer", id: "...", value: "Core" }]
Agente→ [Continua com appetite=Core]
✅ Vantagens
  • UX sob medida — radio buttons, checkboxes, preview, notas
  • Embutido no Mission Control — sem abrir outra aba
  • Histórico de perguntas e respostas visível
  • Pode notificar via Slack, Linear, etc.
⚠️ Desafios
  • Requer construir e manter o componente de perguntas
  • O agente (Pi) precisa de um tool novo para emitir perguntas em vez de ask_user_question
  • Se o web app não estiver aberto, a pergunta fica sem resposta — precisa de fallback
OPÇÃO C

C — Terminal streaming + "Responder aqui" como overlay

🎯 Mostrar o terminal ao vivo e permitir responder clicando em botões na UI

O terminal do Pi é transmitido ao vivo (xterm.js). Quando o agente usa ask_user_question, o Mission Control detecta o padrão no terminal (as opções renderizadas) e exibe um overlay de resposta sobre o terminal — botões clicáveis que, quando pressionados, simulam digitar a resposta no terminal.

Terminal + Overlay de Resposta
┌────────────────────────────────────────────────────────────┐ │ $ pi │ │ ┌─────────────────────────────────────────────────────────┐ │ │ │ ◆ setup:15 — How deep should the plan be? │ │ │ │ │ │ │ │ 1. Lean — Quick validation, 1-2 scopes │ │ │ │ 2. Core — One feature, 3-5 scopes │ │ │ │ 3. Complete — Full pipeline, 8-15 scopes │ │ │ │ │ │ │ │ > _ │ │ │ └─────────────────────────────────────────────────────────┘ │ │ │ │ Responder [ Lean ] [ Core ] [ Complete ] | ✏️ Custom │ │ │ └────────────────────────────────────────────────────────────┘
✅ Vantagens
  • Não requer mudanças no Pi — funciona com o ask_user_question existente
  • PM vê o terminal ao vivo "pensando"
  • Respostas são "click to type" — natural e familiar
⚠️ Desafios
  • Detecção de padrões no terminal é frágil (mudança de prompt, cores, etc.)
  • Se o usuário fechar o navegador, a pergunta fica órfã no terminal
  • Requer o daemon + terminal streaming sempre ativos
🧪

Minha avaliação: A Opção A (Plannotator question-doc) é a mais elegante porque reaproveita algo que já existe. Mas a Opção B (web UI própria) dá mais controle e melhor UX. Uma abordagem híbrida: usar a Opção B como padrão (perguntas no Mission Control) e a Opção A como fallback (quando o Plannotator está disponível mas a web UI não). E a Opção C pode ser um add-on interessante — "ver o terminal ao vivo" como feature extra mesmo que as perguntas sejam respondidas via UI.

🎯 Recomendação Final

Depois de toda a exploração, aqui está uma direção concreta para começar.

🚀 MVP: Daemon + Mission Control + Linear Sync

O que fazer: Construir um daemon Node que observa stelow.json e expele o estado via WebSocket. Um web app (Next.js ou frontend puro) que consome esse WebSocket e exibe um dashboard igual ao mockup acima — workflows, progresso, scopes, artefatos. Um módulo Linear que cria/comenta issues.

O que NÃO fazer no MVP: Terminal streaming ao vivo (complexo, valor médio). Quest engine próprio (comece com a pergunta aparecendo no web app redirecionando para o Pi ou Plannotator). Embed do Plannotator (abrir em nova aba resolve).

Para as perguntas (a grande questão): Comece com a Opção B leve — o web app mostra "pergunta pendente" com um botão que abre o terminal (ou Plannotator) para responder. Depois de validar que PMs usam o web app, evolua para um componente de questionário embutido. A Opção A (question-doc no Plannotator) pode ser explorada em paralelo como experimento rápido.

📦 Aproveitando o que já existe

O Muxy panel (integrations/muxy/stelow/src/panel/) já tem 70% do que o Mission Control precisa:

  • Leitura e parsing do stelow.json (loadTrackingData)
  • Grouping por macro-stage (groupWorkflowsByMacroStage)
  • Progresso de scopes e tarefas (getScopeProgress, getTaskSummaryText)
  • Scanning de artefatos (scanArtifactDirs)
  • Parsing de spec-tech.md para scopes (parseScopesFromSpecTech)
  • Cross-worktree awareness

O Mission Control pode reusar toda essa lógica — o data layer é essencialmente o mesmo. A diferença é que em vez de rodar dentro de um iframe do Muxy, roda como web app independente com backend próprio.

🔮 Visão de longo prazo

O Mission Control pode se tornar a porta de entrada do stelow para não-devs:

  • PM abre o Mission Control, vê workflows pendentes, responde perguntas, aprova gates
  • UX Designer vê os artefatos de interface, anota no Plannotator, aprova o int-gate
  • Dev inicia workflows no terminal (Pi), acompanha scopes no Mission Control, ou abre o terminal streaming para debug
  • Stakeholder vê o board executivo no Mission Control — quantos workflows em andamento, progresso geral, bloqueios

Tudo sem criar "mais uma ferramenta" — o Mission Control é um hub que conecta o terminal (Pi), o projeto (Linear), a revisão (Plannotator), e as pessoas (PM/UX/Dev).
