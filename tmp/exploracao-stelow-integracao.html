stelow além do terminal

Uma exploração de como levar o workflow de planejamento de produto do stelow
para ferramentas que PMs, UX designers e devs já usam no dia a dia.

🔍 Pesquisa exploratória 🧩 Linear + Multica.ai + Plannotator 🎯 Human-in-the-loop preservado

🧠 O problema central

🎯 O valor do stelow

Structured gates, perguntas no momento certo, adversarial critique, Plannotator visual review, typed scopes com dependências explícitas. Um workflow que força clareza antes de executar.

Valor preservar

⚡ A trava atual

Tudo roda dentro do terminal do Pi. PMs e UX designers não vivem em terminais. O ask_user_question exige Pi. Os gates exigem Plannotator + Pi. A adoção depende de devs operando o terminal.

Limitação

🔄 O insight do usuário

Em vez de criar um sistema próprio de gerenciamento (outro dashboard, outra ferramenta), a ideia é integrar com o que as pessoas já usam — Linear, Multica, e manter o Plannotator como superfície visual.

Direção

🧪 Human-in-the-loop

As perguntas intencionais, os gates, as decisões de escopo — tudo isso é o coração do stelow. A questão é: como oferecer isso sem forçar todo mundo a usar o mesmo terminal?

Desafio de design

🏗️ Como o stelow funciona hoje

Entender a arquitetura atual é essencial para ver onde e como podemos inserir novas superfícies de interação.

setup → context → shape → critique → gate → scope
interface → int-gate → planning → plan-gate → execution → diff-gate
📋 ask_user_question plannotator --gate 🧑‍💻 Tudo no terminal (Pi)
💡
Insight: O stelow já tem 3 pontos de interação com humanos bem definidos:
  1. ask_user_question — perguntas estruturadas no terminal (setup, scope, interface selection)
  2. plannotator --gate — revisão visual no browser (gate, int-gate, plan-gate, diff-gate)
  3. Gap resolution — o LLM pergunta ao usuário sobre gaps críticos encontrados na critique

🗺️ O ecossistema disponível

Três ferramentas principais emergem como candidatas a superfície de interação. Cada uma com capacidades e limitações específicas.

📐 Linear

O que é: Gerenciamento de projetos opinativo, dev-first. Referência para times de produto.

API: GraphQL completa — issues, projects, comments, webhooks. Sem custom fields nativos. Tags e labels substituem.

Webhooks: Eventos em tempo real para triggers externos.

Limitação chave: Sem custom fields → estado do stelow (appetite, review_mode) precisaria ser codificado em labels ou description parsing.

Superfície: issues + comments

🤖 Multica.ai

O que é: Plataforma open-source que gerencia AI coding agents como membros de time. Já suporta Pi como runtime.

Modelo: Issues atribuídas a agentes, squads, autopilots (cron), daemon local.

Integração com stelow: Potencial de rodar workflows do stelow dentro do Multica, com gates virando approval steps.

Superfície: agent tasks + daemon

📝 Plannotator

O que é: Superfície de revisão visual interativa no browser. Já é o gate do stelow.

Não é read-only: Suporta anotações bidirecionais, feedback → LLM, approve/reject.

Potencial não explorado: Se Plannotator pode abrir qualquer markdown para anotação, por que não usar para perguntas também?

Superfície: browser interativo

⚡ Tensões de design

Três forças que qualquer solução precisa equilibrar:

📊 Tensão 1 — Terminal vs Browser

O ask_user_question do Pi oferece uma experiência riquíssima (2-6 opções, preview, multi-select, notas laterais) mas está preso ao terminal. Plannotator já está no browser mas foi desenhado para revisão de artefatos, não para perguntas. Como unificar? Fazer Plannotator renderizar perguntas? Ou criar um formato de "documento de perguntas" que Plannotator abre?

🔄 Tensão 2 — Pull vs Push

Hoje o workflow push perguntas para o usuário no terminal (ele vê, responde, continua). Numa integração com Linear, o workflow pull o usuário para o browser/Linear (cria issue com pergunta, usuário vê quando acessa). Isso muda a dinâmica: em vez de "responda agora", vira "responda quando puder". Como o bloqueio (gate) se comporta nesse modelo?

🎭 Tensão 3 — Quem opera?

Hoje o desenvolvedor opera o terminal e responde perguntas. Numa interface tipo Linear, PMs e UX designers podem responder perguntas de escopo e design sem abrir terminal. Mas quem inicia o workflow? Um PM cria uma issue no Linear com label "stelow" e o daemon dispara? Ou o dev continua iniciando no terminal e o convite vai para o PM via Linear?

🧩 Quatro alternativas de arquitetura

Cada opção representa um equilíbrio diferente entre profundidade de integração, esforço de implementação e preservação do valor central do stelow.

IDEIA PROMISSORA

A — Plannotator como interface universal de perguntas

🎯 Foco: transformar cada pergunta em um documento anotável

Em vez de fazer perguntas no terminal via ask_user_question, o workflow gera um "documento de perguntas" estruturado em markdown. Esse documento é aberto no Plannotator no browser. O usuário vê perguntas com opções, seleciona, anota, aprova. O feedback estruturado volta para o LLM.

✨

A chave: Plannotator já suporta checkboxes interativos (- [ ] / - [x]) e anotações linha a linha. Um "questionário" em markdown com checkboxes e campos de annotação + o --gate já existente pode cobrir todo o fluxo de perguntas — sem precisar de uma ferramenta nova.

✅ Vantagens
  • Não requer ferramenta nova — Plannotator já existe
  • Funciona em qualquer browser (PMs, UX, devs)
  • Preserva blocking gate semantics
  • Feedback estruturado via annotations
  • Aproveita o approval receipt existente
⚠️ Desafios
  • Plannotator não foi desenhado para questionários — UX pode não ser ideal para multi-select ou preview
  • Precisa estender o Plannotator ou criar um formato de question-doc
  • Perde a imersão do terminal (pergunta aparece na hora)
PESQUISAR MAIS

B — Linear como superfície de decisão + Plannotator para gates

🎯 Foco: trabalhar onde o time já gerencia projetos

Cada etapa do stelow cria/atualiza uma issue no Linear. Perguntas viram comentários com checkboxes. Decisões viram transições de status. Plannotator gates continuam abrindo no browser. Um daemon leve (tipo o Multica) escuta webhooks do Linear e avança o workflow.

Issue criada → Comentário com pergunta → PM responde → Webhook → Daemon → Plannotator gate
✅ Vantagens
  • PMs/UX vivem no Linear — zero ferramenta nova
  • APIs e webhooks robustos
  • Histórico de decisões fica no Linear
  • Convite natural: "Issue #42 precisa da sua resposta"
⚠️ Desafios
  • Sem custom fields → estado do stelow precisa ser codificado (labels, description)
  • Não é síncrono — perde o "responda agora" do terminal
  • Complexidade de implementação: daemon + webhooks + sync bidirecional
  • Multi-select de opções não é nativo do Linear
PESQUISAR MAIS

C — Multica.ai como orquestrador + stelow como skill

🎯 Foco: delegar o workflow para agentes gerenciados

O stelow vira um skill que roda dentro do Multica. O Pi (suportado) executa o workflow. As perguntas e gates são gerenciadas pelo Multica — que já tem UI web, sistema de issues, squads e autopilots. O daemon local do Multica conecta o terminal à interface web.

✅ Vantagens
  • Zero nova infra — Multica já existe e suporta Pi
  • UI web nativa para acompanhar progresso
  • Autopilots para workflows recorrentes
  • Open-source, self-hostable
⚠️ Desafios
  • Multica é desenhado para coding agents, não para product planning
  • As perguntas estruturadas do stelow não mapeiam 1:1 para issues do Multica
  • Depende do ecossistema Multica evoluir
  • Precisa testar se os gates (plannotator) funcionam dentro do fluxo do Multica
MAIS COMPLEXO

D — App web leve próprio + Plannotator gates

🎯 Foco: experiência controlada, sem depender de terceiros

Um app web minimalista que serve apenas o formulário de perguntas do stelow. O terminal continua rodando a orquestração. Quando chega uma pergunta, o app abre no browser. Usuário responde, fecha, workflow continua. Plannotator gates permanecem como estão.

✅ Vantagens
  • Experiência de perguntas sob medida
  • Pode imitar exatamente o ask_user_question (multi-select, preview)
  • Não depende de evolução de terceiros
⚠️ Desafios
  • Outra ferramenta na vida do time — contradiz o objetivo
  • Precisa ser mantida, testada, documentada
  • Pode virar um projeto paralelo que nunca termina

🔬 Síntese e questões abertas

🚀

Minha recomendação inicial: explorar a Opção A (Plannotator como question-doc) primeiro. É a que menos requer infraestrutura nova, mais aproveita o que já existe, e resolve a tensão central: como levar as perguntas para fora do terminal sem perder a semântica de blocking gate.

A Opção B (Linear) pode ser um complemento natural depois — o question-doc vira um artefato linkado numa issue do Linear, e o time vê o progresso do workflow no board sem precisar abrir terminal.

❓ Perguntas que ainda precisam de resposta

  • 1 O Plannotator consegue renderizar checkboxes interativos e retornar quais foram selecionados? Sabemos que ele renderiza - [x] visualmente, mas o feedback (annotations) captura o estado? Precisamos testar.
  • 2 E se o Plannotator for estendido? Em vez de apenas anotar, ele poderia ter um modo "questionário" — radio buttons, checkboxes, text input? Isso abriria a possibilidade de ter perguntas ricas no browser sem nenhuma outra ferramenta.
  • 3 O que acontece com o Review Mode Auto? No modo Auto não há perguntas. Se movermos as perguntas para Plannotator, o Auto vira "gerar documento de perguntas mas não abrir Plannotator"? Ou o documento nem é gerado?
  • 4 Linear Agents API — A nova API de Agents do Linear permite criar "co-workers" programáticos que interagem com issues. Um "Linear Agent stelow" poderia escutar webhooks, fazer perguntas via comentários, e avançar o workflow? Isso merece pesquisa mais profunda.
  • 5 O daemon do Multica já suporta Pi. Se instalarmos stelow + pi + plannotator num ambiente Multica, o que funciona de imediato? O ask_user_question apareceria onde? Precisamos testar na prática.
  • 6 E o Pulse? O sistema de inbox do stelow (Pulse) já processa itens automaticamente com review_mode=Auto. Como ele se comporta se o workflow for iniciado de uma issue do Linear?

Pesquisa

Instalar Multica com suporte a Pi, configurar stelow como skill, e testar um workflow completo. Ver onde as perguntas aparecem e se os gates funcionam.

Prova de conceito

Mesmo sem implementar, definir como seria um "documento de perguntas" em markdown — frontmatter com metadados, seções de perguntas, opções com checkboxes, campos para notas. Isso esclarece se a abordagem é viável.
